# JutJut Student UX and Product Audit

**Overall assessment.** JutJut communicates a compelling student proposition: turn verified evidence into access to work, practical learning, and perks. The platform is strongest where it makes institutional approval, consent, or redemption state explicit. However, the current student journey contains a consequential split between prototype UI state and protected backend state. A student can be shown a successful action that is not recorded, or be redirected to external authentication after the prototype shell treats them as signed in. Resolving those seams should precede further feature expansion.

> **Scope note.** The supplied preview was inspected. Its local demo sign-in rendered the dashboard, but navigating to a protected data experience redirected the browser to the Manus authentication portal. Findings for protected flows are therefore cross-checked against the implemented client and server code, rather than inferred from unavailable live outcomes. [1] [2] [3]

## What already supports student value

The public page clearly states that the service is free to students, requires no card, and gives students control of their data. It names the four core outcomes—Kit, jobs, perks, and university pathways—and carries the Practicals destination through sign-in rather than losing the intended task. [1] [4] The Practicals student workspace is the most coherent end-to-end journey: first-visit guidance explains the three steps, only course-linked approved opportunities appear, empty states give a next action, and the institution remains visibly responsible for final approval. [5] [6]

The profile privacy surface is unusually strong. Students can preview the employer view, see which identity fields are hidden, change contact sharing, and read the important limitation that consent is snapshotted at application time. [7] The QR redemption component also includes useful loading, expiry, refresh, retry, and confirmed-redemption states, backed by a ten-minute, student-scoped token policy. [8] [9]

The visual system has a good structural baseline: skip links, dark mode, clear card boundaries, responsive grid breakpoints, and a global Quiet Mode that persists and removes motion. Jobs includes usable search, filters, saved-job and no-results recovery; My Kit includes a vouch loading skeleton and a purposeful empty state. [10] [11] [12]

## Prioritised findings

| Priority | Finding and implementation evidence | Safe, in-scope recommendation | Expected impact and measure |
|---|---|---|---|
| **P0** | **Job application completion is not connected to the durable application path.** The Jobs UI calls the client-context `applyToJob`, which only looks up mock IDs and shows a toast. It does not call the existing `employer.jobs.applyForJob` mutation or `recordView`. Database-sourced jobs are mapped to numeric-string IDs, so they do not match the mock `job-*` IDs used by that handler. The confirmation also presents fixed example evidence rather than the student’s actual Kit. [11] [2] [13] | Replace the context-only handler with the existing application mutation, pass the real job ID, disable while pending, show duplicate/server errors inline, and invalidate or add a simple “My applications” status view. Populate the confirmation from the same employer-view/consent data used by the privacy preview. | Restores the central Jobs promise and makes applications, views, and hires measurable. Track **listing view → apply confirmation → successful application**, duplicate/error rate, and time to first application. |
| **P0** | **Authentication has two competing truths.** The app shell accepts `jutjut_auth` in local storage and the demo Login accepts any email, while feature queries use OAuth-backed `useAuth`. A global tRPC error handler redirects an unauthenticated protected query to Manus sign-in. This was observed after the preview dashboard loaded. [2] [3] [14] | Use the OAuth session as the sole authenticated state for the shell and protected pages; keep any demo access behind an explicit development-only mode. Preserve the existing pending destination after real sign-in. | Removes dead-end redirects and gives conversion reporting a trustworthy denominator. Measure **sign-in start → authenticated return → intended destination reached**, plus unauthenticated redirect loops. |
| **P1** | **The student home prioritises staff tooling over the student’s next outcome.** The visible dashboard includes “System Admin Settings,” payment credential instructions, and links to admin pages. The general navigation also exposes Brand Assets and Teacher Portal to every authenticated user. In the observed student dashboard, these compete visually with completing a Kit, requesting a vouch, or finding work. [12] [15] | Role-gate admin, teacher, employer, and brand links. Use the recovered space for one context-aware student next step—e.g. “Request a vouch” or “Complete your Kit”—and label **My Kit** once as “your verified profile.” | Reduces cognitive load and increases first-session activation. Measure **first-session Kit action rate**, vouch request rate, and time from dashboard arrival to a value action. |
| **P1** | **Prototype and live-data signals are contradictory.** Jobs and The Drop disclose sample data, but the dashboard itself renders hard-coded social content and cross-market examples, while the landing page positions the service for Australian students. The Drop always renders a hard-coded Chipotle hero; its database list returns active drops only, marks mapped drops unclaimed, and therefore cannot truthfully supply the page’s past/upcoming states or claimed state. [1] [12] [16] [9] | Put all sample content behind one clearly labelled preview-data boundary. In live mode, render database-backed active offers only; show a helpful “No Drop this week yet” state when none exist. Use the same availability and claim state in the card and QR flow. | Prevents avoidable trust loss and false urgency. Measure **eligible students shown a live offer**, QR generation rate, redeemed-QR rate, and support/failed-claim rate separately from preview traffic. |
| **P1** | **The Drop and Practicals blur student and provider roles.** A student can switch The Drop to “Business Partner Hub,” where submission is merely protected rather than business-role-gated. Any user can also choose business or institution tabs in Practicals, then encounter setup or permission-oriented content. [16] [5] [17] | Render student-only default views for student accounts. Gate provider views and mutations by the existing role/profile checks; if retained for discovery, present them as a short “Interested in hosting?” explanation rather than an editable workspace. | Builds confidence that student areas are for students and lowers navigation misfires. Measure **wrong-role tab visits**, denied submission attempts, and completion of the student’s primary task. |
| **P1** | **Data failures can look like normal empty or sample content.** Jobs and The Drop default their queries to empty arrays but do not render loading or query-error states. The Dashboard requests feed data but displays its fixed `posts` array instead. Practicals handles initial skeletons well, yet several status lists similarly default failed queries to empty. [11] [12] [16] [5] | Add compact skeletons on initial fetch and an explicit error-with-retry state in each student list. Do not silently substitute sample cards after a live query fails; reserve samples for explicit preview mode. | Makes absence interpretable rather than deceptive and improves recovery. Measure **query failure → retry → recovered session** and distinguish true-empty inventory from technical errors. |
| **P2** | **Accessibility claims currently exceed the implemented scope.** Quiet Mode is real and persistent, but “Task Breakdown” changes only a demonstration profile form in Your Way, not high-friction My Kit, Job, or Practicals forms. “Simplify Job Boards” swaps supplied descriptions only. The custom setting controls are buttons without switch semantics or `aria-checked`, while the landing copy promises plain language across the platform and one-question-at-a-time forms. [10] [18] [1] | Keep the useful controls, add semantic switch state and visible focus treatment, and apply the existing stepped-form pattern first to the vouch request and practical application dialogs. Phrase plain-language support precisely until it is truly cross-product. | Better completion for students who need reduced cognitive load without a redesign. Measure **form abandonment and completion by setting enabled**, keyboard completion rate, and accessibility-related support feedback. |
| **P2** | **Students cannot yet see a credible return on their effort.** The Kit displays a fixed verification score and the Jobs flow lacks an application history, although the backend already has application, job-view, employer analytics, QR redemption, and practical-status records. Practicals does expose application outcomes, demonstrating the appropriate pattern. [19] [13] [9] [5] | Replace the fixed score with a brief, explainable completion summary (“1 of 3 evidence types added”) and surface existing application/verification states in My Kit or Dashboard. Instrument the existing records rather than building a separate analytics product. | Connects evidence-building to outcomes and enables ROI assessment. Report **vouch request→verification time**, **Kit completion→application rate**, **application→interview/hire where recorded**, **Drop claim→redemption**, and **practical link→approval→completion**. |

## Highest-leverage sequence

First, unify real authentication and connect Jobs to the application and view-recording procedures. These changes protect the main student value proposition and establish reliable conversion data. Next, remove mixed-role and staff surfaces from the student path, then make sample/live inventory and empty/error states truthful. Finally, reuse the existing Practicals stepped-flow and status patterns in My Kit and Jobs so accessibility and outcome visibility become product behaviour rather than marketing claims.

No application source files were changed for this review. The project’s full test suite passed at the audit baseline (**389 tests**), and `pnpm check` completed successfully.
